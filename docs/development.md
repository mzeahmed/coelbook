# Development Guide

How the code is organized and the conventions to follow when changing it. For running the environment, see the [README](../README.md#getting-started-development).

---

# Project layout

```text
api/                     Go API
  cmd/                   entry point (main.go)
  internal/
    modules/<name>/      one package per feature: module.go, handler.go, service.go, dto.go
    database/
      migrations/        goose SQL migrations (also the schema sqlc reads)
      sqlc/              SQL queries, one file per entity
      queries/           Go code generated by sqlc — never edit by hand
    apperr/              errors with a stable code (see "Error codes")
    response/            JSON envelope helpers
    middleware/          auth, recovery, logging, JSON 404/405
    slug/                URL identifiers from names
    router/              wires every module's routes
  openapi/               OpenAPI specification
frontend/                React + TypeScript (Vite)
  src/
    http/                fetch wrapper (client.ts) and error messages (errors.ts)
    modules/<name>/      api.ts, views/, components/, lib/
    router/              routes and their guards
docs/                    architecture, guides, releases
scripts/                 helper scripts used by the Makefile
```

# API

## Modules

Each feature is a package under `api/internal/modules` exposing a `Module` with a `New` constructor and a `RegisterRoutes(mux, authenticate)` method, registered in `api/internal/router/router.go`. Routes that need a signed-in user are wrapped with `authenticate`.

Scaffold a new one with:

```bash
make module m="name"
```

Within a module, the **handler** decodes and validates the request (`dto.go`'s `Validate`), calls the **service**, and maps its errors to HTTP statuses. The **service** holds the logic and talks to the database through sqlc queries; writes touching several tables run in one transaction.

## Database

- Schema changes are **goose migrations** in `api/internal/database/migrations`. Create one with `make migrate-create t="name"`. They are embedded in the binary and applied when the API starts (`AUTO_MIGRATE`, on by default), in development as in production; `make migrate-up` / `make migrate-down` apply or roll back by hand. Every migration has a working `Down`.
- Queries are plain SQL in `api/internal/database/sqlc/*.sql`. After changing a query or a migration, run `make sqlc` and commit the generated `queries/` code.
- `incidents.search_vector` is not maintained by the database: the incident service refreshes it after every write (see [data-model.md](architecture/data-model.md)). Code that writes incidents, their tags or their snippets must do the same.

## Responses and error codes

Every response uses the envelope `{code, success, error, field, message, data}`.

Errors carry a **stable code** in `error` (e.g. `title_required`); `message` is an English, developer-facing description that may change. Validation errors also set `field` to the path of the offending input (`title`, `snippets[2].content`).

- Create errors with `apperr.New(code, message)` or `apperr.NewField(code, field, message)`, and write them with `response.AppError(w, status, err)`. Any other error becomes a generic `internal_error` 500, so internal details never leak.
- **Every new code must be added in two places**: the `error` enum of the `Envelope` schema in **every** OpenAPI file (each file of `api/openapi/paths/` is a standalone document with its own copy of the envelope), and the French message map in `frontend/src/http/errors.ts`.

## OpenAPI

The specification lives in `api/openapi/paths/`, one standalone OpenAPI document per area (`incidents.yaml`, `tags.yaml`, `auth.yaml`…), each carrying the shared components it uses. Update it in the same change as the endpoint.

The rationale for every declared npm and Go dependency is listed in
[dependencies.md](dependencies.md). Consult it before adding, replacing or
upgrading a dependency.

# Frontend

## Language

Everything displayed in the browser is in **French**: labels, buttons, placeholders, messages, empty states, `aria-label`s and titles. Code, comments and documentation are in **English**.

API error messages are never displayed: show `errorMessage(err)` from `frontend/src/http/errors.ts`, which translates the error code.

## Conventions

- API calls go through `apiFetch` (`src/http/client.ts`), which unwraps the envelope and throws an `ApiError` carrying the HTTP status, the error code and the field.
- A `401` sends the user back to `/login` after clearing the session.
- Forms use `noValidate` and rely on the API's field errors, so validation messages are always in French.
- Pages that pull in Markdown rendering or syntax highlighting are lazy-loaded routes, to keep the main bundle small.
- Colors come from the CSS variables in `src/assets/design-system.css`.

The frontend container keeps its own `node_modules`: after adding a dependency, run `docker exec coelbook_frontend npm install` (or `make restart`).

# Quality checks

```bash
make check                      # go fmt, go vet, go test
cd frontend && npm run lint     # ESLint
cd frontend && npm run build    # type-check and production build
```

CI (`.github/workflows/checks.yml`) runs the Go checks and the frontend checks (ESLint, type-check, build) on every pull request and on pushes to any branch but `main`. Pushing a version tag runs `.github/workflows/release.yml`, which publishes the image and the GitHub release (see [versioning.md](releases/versioning.md#creating-a-release)).

# Git workflow

- Start a branch from `develop` (short, `snake_case` names such as `full_text_search`), open a pull request into `main`, and squash-merge it. `update.yml` then merges `main` back into `develop`.
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org): `feat(scope): …`, `fix(scope): …`, `docs(scope): …`, `chore(scope): …`.
- `make clean-branches` deletes every branch except `main` and `develop`, locally and — for the repository owner only — on GitHub.

Releases follow [versioning.md](releases/versioning.md) and are recorded in the [CHANGELOG](../CHANGELOG.md).
